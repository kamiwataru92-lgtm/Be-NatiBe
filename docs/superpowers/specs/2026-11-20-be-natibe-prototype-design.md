# Be-NatiBe 試作品 設計書

日付: 2026-11-20
状態: レビュー待ち

## 1. 何を作るか・なぜ作るか

**Be-NatiBe** は、文法の正確さよりも「ネイティブと自然に通じ合えること」を重視した言語学習アプリ。最初の対象言語はアメリカ英語。

- **鍛える力**
  - スラング・イディオム（ネイティブが実際に使う表現）
  - リスニング（ナチュラルスピードや崩れた発音の聞き取り）
  - 文章構成力（言いたいことを組み立てて相手に伝える力）
- **想定ユーザー**: 日本語を母語とする学習者。中学英語（義務教育）程度の人から、TOEIC満点でも話せない人まで
- **今回の位置づけ**: 一般公開ではなく試作品。学習の流れそのものが効果的か、使っていて楽しいかを早く確かめることが目的

## 2. ゴール / 非ゴール / アンチゴール

**ゴール**
- 1回10分ほどで「聞く → 表現を拾う → 自分で返す → フィードバック」の流れを一通り体験できる
- レベル差の大きいユーザーが、それぞれ無理のない難易度で使える
- iPhone のブラウザでも PC でも、URL を開けば使える

**非ゴール（今回はやらない）**
- ログイン、アカウント、サーバー側での学習履歴の保存
- 課金、利用量の管理
- ネイティブアプリ（iOS / Android）
- アメリカ英語以外の言語の中身（差し替えられる作りにはしておく）
- 高品質な音声 API（後から差し替えられる作りにしておく）

**アンチゴール（動いても失敗とみなすもの）**
- 文法の細かい誤りを赤ペン添削するアプリになる。フィードバックの主役は「通じたか」「ネイティブならこう言う」であるべき
- 教科書のような会話しか出てこない。スラングや崩れた言い方が出てこなければ意味がない
- 上級者にとって簡単すぎる、または初心者にとって何もわからない

## 3. 制約

- 対象言語はアメリカ英語。ただし、言語ごとの設定（AI への指示、読み上げの言語コード、解説の言語など）を1か所にまとめ、将来の言語追加に備える
- 試作品なので、運用コストと準備の手間は最小限にする。外部サービスは AI（Claude API）のキー1つだけ
- API キーをブラウザに露出させない（サーバー側から呼ぶ）

## 4. 検討した作り方

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A（採用）** | Web アプリ。AI は Claude、読み上げと音声入力はブラウザ内蔵機能 | どの端末でも URL で使える。必要な鍵は1つ | 読み上げがやや機械的で、崩れた発音のリアルさが弱い |
| B | A と同じ構成で、読み上げを高品質音声 API（ElevenLabs 等）にする | リスニングの質が高い | 追加の API キーと利用料が必要 |
| C | iPhone ネイティブアプリ | 操作感が最良 | Mac / Xcode が必要。試作としては遠回り |

**A を選んだ理由**: 試作の目的は学習の流れを確かめること。読み上げ部分を差し替えられる作りにしておけば、流れが良いとわかった時点で B に移れるので手戻りがない。（ユーザーが選択）

## 5. 1回の学習の流れ（ユーザーと合意済み）

1. **聞く**: カフェでの雑談や友達とのメッセージのような、ネイティブ同士の短い自然な会話（4〜8往復程度）を聞く。gonna / wanna / y'know のような崩れた言い方もそのまま含める。台本は最初は隠しておき、あとで表示できる
2. **表現を拾う**: 会話に出てきたスラングやイディオムを3〜5個取り上げ、日本語の解説、使う場面、カジュアルさの度合いを示す
3. **自分で返す**: AI のネイティブキャラと同じ場面で会話する。テキスト入力か音声入力（ブラウザの音声認識）で返し、拾った表現を使うよう促す
4. **フィードバック**: 次の3点を返す。文法の細かい誤りは、意味が通じなくなる場合だけ指摘する
   - 通じたか（相手にどう伝わったか）
   - ネイティブならこう言う（より自然な言い換え）
   - 話の組み立て（言いたいことの順番や、つなぎの言葉をこうすると伝わりやすい）

## 6. レベル対応（ユーザーと合意済みの方針）

- 初回に短い診断を行い、開始レベルを決める。内容はリスニング数問と、簡単な返答1〜2問
- レベルは3段階程度を想定（細かさは作る人に任せる）
  - **初級（中学英語程度）**: 読み上げはゆっくり、日本語の解説は多め、表現は「これだけで通じる」定番から
  - **中級**
  - **上級（TOEIC 高得点だけど話せない層）**: ナチュラルスピード、スラングを遠慮なく使う。「正しいけど教科書っぽい」言い方を、ネイティブらしい言い方に直す方向。自分で返す練習の比重を増やす
- ユーザーは自分でレベルを変更できる

## 7. 技術構成（Claude 側の判断。ユーザーは作り方を任せている）

- **フレームワーク**: Next.js（App Router）＋ TypeScript。画面と、API キーを隠すためのサーバー側処理を1つにまとめられる
- **AI**: Claude API（Anthropic SDK）を、Next.js のサーバー側ルートから呼ぶ。次の用途で使う
  - 会話教材の生成（場面、レベルに応じた台本、取り上げる表現と解説）
  - ネイティブキャラとしての会話
  - フィードバック生成
  - 診断結果の判定
  - モデル名は環境変数で切り替えられるようにする。既定値は作る人が速度とコストを見て決める
- 教材（会話・表現・解説）は構造化データ（JSON）で返させ、画面側で組み立てる
- **読み上げ**: ブラウザの音声合成機能（Web Speech API の SpeechSynthesis、en-US）。「読み上げ担当」の差し替え口を作り、将来は高品質音声 API に替えられるようにする。会話の話者ごとに声を変える（使える声がある範囲で）
- **音声入力**: ブラウザの音声認識機能（Web Speech API の SpeechRecognition）。使えないブラウザではテキスト入力だけにする
- **保存**: レベル、学習回数、覚えた表現のリストはブラウザ内（localStorage）に保存。サーバー側の保存はしない
- **言語設定**: 対象言語ごとの設定（言語コード、AI への指示文、場面リストなど）を1つの設定ファイルにまとめる
- **公開先**: Vercel などの簡単なホスティングを想定。この環境ではローカルで動作確認まで行う
- **スマホ対応**: iPhone の Safari で使える画面幅・操作感にする

## 8. 作る人に任せる部分

- 画面デザインの細部（見た目の方向性、配色、レイアウト）
- 場面（カフェ、職場の雑談、パーティー、SNS など）の具体的なリストと数
- 診断問題の具体的な中身と、レベルの段階数
- AI への指示文の書き方、JSON の項目の具体的な形
- 使用するモデルの既定値
- テストの範囲（試作品なので、AI の出力形式の検証や主要な処理に絞ってよい）
